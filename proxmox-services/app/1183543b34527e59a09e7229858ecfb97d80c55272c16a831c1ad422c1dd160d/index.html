The Proxmox VE host is the heavy compute and storage node: eight lightweight Linux containers (LXC) for databases, automation, development, media and the Docs platform, plus a dedicated backup server. It is switched on when needed, which keeps the power bill small.

Why LXC containers

LXCs share the host kernel, so each one costs a few hundred MB instead of a whole virtual machine. Docker runs inside some of them ("Docker hosts"), while others run a single native service managed by systemd.

Why on demand

The server idles at a few watts but a Ryzen box still costs more than a Pi. The always-on Pi wakes it with Wake-on-LAN and starts or stops individual containers through the API, so only what you use is running.

Why a separate backup server

Proxmox Backup Server de-duplicates and compresses, so seven nightly copies of every container fit on a 240 GB SSD. It lives on its own disk, apart from the data it protects.

Roadmap. The media pool is a single disk and, being a mount point, is not part of container backups. A mirror (or a second copy) is planned before it passes about 85 % full.

The nightly job

  1. 04:30 every day the scheduler runs on all containers, stopped ones included.
  2. Mode is snapshot: running containers keep running.
  3. Each backup goes to the Backup Server; the job keeps the newest seven per container.
  4. A report is mailed to the owner.

What is protected

  • Every container: root disk and config
  • The Raspberry Pi: weekly full-disk backup
  • Not included: the media volume (a mount point) and the host's own settings, which are kept as files in a repository

The power model, and what it means for backups

After a reboot

Only the Backup Server container has onboot set, so it comes up first. Everything else waits to be started from the Hub or with pct start.

Gaps are normal

Backups only run on days the host happens to be awake. There is no catch-up, so a missed night is a missing night. Before shutting the server down for a long time, take a manual backup.

Roadmap for the backup side: a scheduled prune and garbage-collection job on the Backup Server, a verify schedule and a copy outside the house.

The host can be rebuilt from a bare machine because its settings are kept as files and every container is in the backup datastore, which sits on its own disk.

  1. Install Proxmox VE on the NVMe only, with the data disks unplugged so the installer cannot touch them. Set the fixed address and hostname.
  2. Reattach the disks. Mount the backup SSD by UUID; import the ZFS pool (never create over it).
  3. Apply the host settings: Wake-on-LAN unit, firewall files, storage definitions and the backup job, from the saved configuration files; join Tailscale.
  4. Bring the Backup Server back first (from its own dump or by reinstalling and re-adding the existing datastore), then add it as pbs-remote.
  5. Restore containers in dependency order: database, web and AI host, automation, dev box, agent server, Docs, then the media container (reattach its ZFS volume instead of creating a new one).
  6. Verify storage status, the container list, the Hub, the public pages and that the next backup run creates new snapshots.
