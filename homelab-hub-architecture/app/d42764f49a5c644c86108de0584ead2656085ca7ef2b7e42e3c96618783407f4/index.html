Homelab Hub Field Guide

Homelab Hub is a self-hosted control panel for a small home lab, and Docs is its companion knowledge base. Together they run on two cheap machines: a Raspberry Pi 4 and a small container on a Proxmox server. This guide explains what each part does, how the parts are connected, who is allowed to reach what, and how to run your own copy.

The Hub private

One container on a Raspberry Pi. Only reachable from your home network or your private VPN (Tailscale).

  • A live dashboard of your services, with status lights and host widgets
  • A YAML config you edit in the browser, with validation, a diff before saving and version history
  • Wake-on-LAN and Proxmox power actions that need a typed confirmation and are written to an audit log
  • A shared-expenses page, a browser terminal and a Docker manager

Docs private editor public pages

Four containers in a small Proxmox container (LXC). The editor is private; the pages you choose to publish are public.

  • A Confluence-style page tree with a rich editor, history, diffs and a Trash
  • Interactive web-app pages (HTML or a ZIP) that run in a locked-down sandbox
  • Each page can get its own public hostname, such as notes.example.com, and visitors see only that page
  • The public portfolio is edited here and served from here

Principles that shaped the design

Editors are never on the internet

The two apps that can change things have no public route at all. The public side is a separate, much simpler program.

The public side has nothing to steal

It has no database driver, no credentials and no admin routes. It only reads a sanitised snapshot file. The build fails if that ever changes.

Two machines, no runtime link

The Pi and the Docs container never call each other. The Hub only links to Docs; your browser does the navigating. Either side can be off without breaking the other.

Dangerous actions need intent

Power actions use a one-time token bound to your session and, for destructive ones, a typed confirmation. Everything is audited.

Boring, testable technology

Java 17 with Spring Boot, plain JDBC, SQLite and React. Hundreds of unit, integration and real-browser tests run before anything is deployed.

Small enough for a Pi

The Hub uses roughly a quarter of a gigabyte of memory. Settings are explicit because Pi kernels often ignore container memory limits.

The Hub is the part you open every day. Everything below lives in one container (hub-internal) on the Pi.

Dashboard

Groups of service tiles with live status (TCP, HTTP or ping checks). A status that cannot be determined shows as unknown, never as an outage. Optional widgets show host CPU, memory, disk, temperature, uptime and network, plus Proxmox resources and a web-search box. Updates stream in live; Ctrl+K opens a search palette for services, actions and pages.

Config editor

The whole dashboard is one text file, dashboard.yaml. The editor validates it on the server, marks the exact line of every error, shows a diff before saving and keeps a version history. If someone edits the file over SSH while you have it open you get a conflict dialog. A broken file never takes the dashboard down: the last good version keeps being served.

Power actions

Wake-on-LAN, and Proxmox start, stop and shutdown for guests and hosts. An action first asks the server what it would affect, then needs a one-time token (valid 30 seconds, bound to your session). Destructive ones need the guest name typed. The UI then follows the real Proxmox task to the end, so it shows the actual result, not just "sent". Every attempt goes to an audit log.

Budget

Shared monthly expenses for a household. People, expenses, equal splits in exact integer paise, part payments, balances that carry over, recurring entries and a "who pays whom" list netted across everyone. Export a PDF for a month or any date range. The page loads only when opened and runs no background job.

Terminal

A shell in the browser, including in the installed phone app. It is off by default. Turning it on needs a login, then asks for your password again for every session. A one-time ticket opens an SSH connection to a pinned host as a dedicated low-privilege user. Idle and maximum-time limits apply.

Docker manager

List, start, stop, restart, update and remove containers on several hosts over SSH, tail and search logs live, create and deploy compose stacks with versioned history, run a container from a form that shows the exact command, and clean up unused images. Protected containers and the Hub itself are refused.

Installable phone app

Served over Tailscale HTTPS the dashboard installs as a progressive web app. Its service worker caches only fingerprinted assets and an offline page, never API responses.

Portfolio card

The portfolio used to be edited here. It now lives in Docs; the dashboard shows a card with two plain links, Edit in Docs and Open public site. The Hub makes no request to the Docs machine.

Docs is a small wiki for notes, runbooks and interactive pages. It is a separate application with its own login, its own database and its own machine.

Write

A page tree you can drag to reorder, with Move to… for keyboard and phone, duplicate, and a 30-day Trash. The editor handles headings, lists, checklists, tables, images, code with highlighting, callouts, collapsible sections, attachments, links between pages and Mermaid diagrams.

Web-app pages

Upload an index.html or a ZIP and it runs as an interactive page in a sandboxed frame. It cannot see Docs, its cookies or its API. The frame can load files from its own bundle, plus the CDNs you tick for that page. This very guide is such a page.

Publish

Pages are private until you give one a public hostname and press Publish. A visitor on that hostname sees exactly that one page, read-only, marked noindex. A hostname the page server does not know gets an empty 404, and once a page is unpublished its address has no route at all. Links to unpublished pages become plain text.

History

Every save, publish, restore and move is a version. Compare two versions with a diff and restore any of them into the draft. A draft change never reaches the public page until you publish.

Portfolio

A one-page portfolio with a filter panel: pick skills and the whole page narrows to matching roles, projects and homelab entries. It is edited at #/portfolio inside Docs, with field-level validation and optimistic locking, and published automatically to its own public hostname.

Backups

The database is copied nightly (14 kept). Images and attachments live in a content-addressed blob folder that the copy does not include, so the whole container is also backed up from Proxmox.

How a page goes public

  1. You press Publish and choose a hostname. The editor records a published version in its database.
  2. The publisher copies the needed files, writes the page's JSON, and writes a host-to-page map last, with an atomic rename. That last write is what makes the page live, so a crash half-way can never expose a half-published page.
  3. The page server notices the map changed and reloads it. It only has read access to that folder.
  4. With route automation on, the editor then calls the Cloudflare API to add that hostname's tunnel rule and a proxied DNS record. The call is queued and retried, so a Cloudflare problem shows as a status with a Retry button and never breaks the publish. Unpublish, delete or rename removes both again. There is no wildcard.
  5. A visitor's request arrives through the Cloudflare tunnel. The server picks the page by the Host header and serves it, or an empty 404.

The goal: a mistake or compromise on the public side must not be able to reach the powerful side, and a mistake in the browser must not be able to switch a server off by accident.

AreaWhat protects it
Public surfaceSeparate containers with no database driver, no Proxmox client and no Spring Security, enforced by a build rule. They read a sanitised snapshot (size-capped, last good copy kept). The public JavaScript bundle is scanned at build time for leaked admin code. Non-root user, read-only filesystem, all Linux capabilities dropped, no-new-privileges.
Network exposureThe editors have no public route. The Docs tunnel's compose network contains only the tunnel connector and the two public servers, so even a wrong tunnel rule cannot reach an editor. The public servers publish no host port. The editor's only outbound call is the optional route automation to the Cloudflare API; the tunnel connector still has no network path to it.
Cloudflare automationOff by default, with a dry-run mode that only logs. The API token is limited to Tunnel: Edit and DNS: Edit on one account and zone and lives only in the editor's .env. Hostnames must be one lowercase label under the zone; wildcards, the main domain, names starting with _ and a reserved list (mail, vpn, other apps) are refused. The tunnel config is read, merged and written back under one lock so every other rule stays, with the 404 catch-all last. Only DNS records carrying a managed-by comment are ever deleted. Every change is in the audit log.
LoginOne bcrypt-hashed password (cost 12), cookie HttpOnly; SameSite=Strict. No default password. Failed logins are rate-limited per client with an escalating lockout, plus a global cap.
CSRF and originCookie-to-header CSRF token on every state change, and a Host allow-list against DNS rebinding.
Content securityStrict CSP, nosniff, self-hosted fonts and icons, link schemes checked, external links use noopener noreferrer.
Power actionsPrepare then confirm with a 30-second one-time token bound to one action and one session. Typed confirmation for destructive actions. Per-target lock. Audit log.
Proxmox accessTLS certificate pinning by default, short timeouts, no redirects, and the API token never appears in logs or errors.
SecretsOnly as ${secret:NAME} references, resolved from a mode-600 file or the environment. A plaintext credential in the YAML is a validation error. Nothing secret is committed to the repository.
Terminal and DockerOff unless enabled, and they refuse to run without a login. Hosts must be declared in the config. SSH host keys are pinned, keys are public-key only and restricted to the Hub machine, commands are built on the server from a fixed set of verbs with every value validated and quoted.
Docs sandboxPage bodies are whitelisted JSON, never HTML. Web apps run in sandbox="allow-scripts" with no same-origin access and a CSP that blocks outside requests. ZIP uploads are checked for path traversal, symlinks, bombs and file types.
Known limits, stated plainly. Legacy Wake-on-LAN URLs stay open (no login) so old callers keep working; cross-site browser requests are refused and every call is audited. Over plain HTTP on the LAN the session cookie cannot be Secure; use Tailscale HTTPS for that. Anyone with the Hub password can open a shell on the Pi once the Terminal is enabled; that is an accepted risk of the feature.

You need a Raspberry Pi 4 (or any Linux box with Docker) for the Hub, and optionally a small Proxmox container with Docker for Docs. Nothing here needs a cloud account except Cloudflare, and only if you want public pages.

Hub on the Pi

  1. Clone the repository and run scripts/build-all.sh. It builds the web bundles, runs every test, and packages the jars.
  2. Create the password hash with the built-in hash-password command, copy deploy/.env.example to deploy/.env and fill it in. Create secrets.env for tokens (mode 600).
  3. Pin your Proxmox certificate with the fingerprint command and compare it with what the Proxmox UI shows.
  4. Start it: docker compose -f deploy/docker-compose.yml --env-file deploy/.env up -d --build. Open http://<pi>:3010, sign in and edit dashboard.yaml in the Config page.

Docs on the LXC

  1. Create the LXC and install Docker. Optionally install Tailscale and expose the editor with tailscale serve.
  2. Create a Cloudflare tunnel for Docs. Add a route for the portfolio hostname pointing at the portfolio server. Routes for published pages are added for you by route automation (next steps), so no wildcard is needed. The first matching rule wins and the last rule must stay the 404 catch-all.
  3. Copy deploy/docs/.env.example to deploy/docs/.env and fill in the password hash and tunnel token.
  4. Optional, route automation: create a Cloudflare API token limited to Cloudflare Tunnel: Edit and DNS: Edit for your account and zone, and set the DOCS_CF_* values in .env (account, zone, tunnel, zone name, token). Start with DOCS_CF_DRY_RUN=true to read the planned calls in the log, then switch to DOCS_CF_AUTOMATION_ENABLED=true with dry run off. Publishing a page now creates its route, and a start-up pass fixes any drift.
  5. Start it: docker compose -f deploy/docs/docker-compose.yml --env-file deploy/docs/.env up -d --build. No container depends on another, so each one starts and restarts alone.
  6. Add a docs: block to the Hub's dashboard.yaml so the dashboard links to it.

The editors are never on the internet. Both private apps are reachable only from the home network and Tailscale. The only things the internet can touch are the two read-only public servers. The one connection the other way is the editor calling the Cloudflare API, outbound only, when route automation is on.
Independence. Stop the Docs editor and the public portfolio and published pages keep working from their last snapshot. Turn the whole Docs container off and the Pi's dashboard is unaffected. Turn the Pi off and Docs is unaffected.
