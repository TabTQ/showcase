The Raspberry Pi 4 is the always-on gateway of this home lab. It sips power, so it stays up 24/7 and hosts the things that must always answer: the control panel, the outbound tunnel to Cloudflare, monitoring and the weekly backup. The big Proxmox server can then sleep until it is needed.

What it does always on

  • Control panel: the Homelab Hub with status lights, power buttons, budget tracker, terminal and Docker manager
  • Front door: a Cloudflare tunnel, outbound only
  • Private access: Tailscale, installed natively
  • Health: Prometheus, Grafana, node-exporter and cAdvisor
  • Upkeep: Watchtower for image updates, a cron job for backups

What moved away

A Pi is small, so anything that duplicated the Hub was retired and its files kept for a quick return:

  • Homepage dashboard replaced by the Hub
  • Standalone Wake-on-LAN service folded into the Hub
  • Guacamole replaced by the Hub's browser terminal
  • Portainer removed to free a port
  • The public portfolio moved to a Proxmox container

Design choices worth knowing

Host networking for the Hub

Wake-on-LAN is a broadcast. A Docker bridge swallows it, so the Hub container uses the host network. It compensates with a read-only filesystem, all Linux capabilities dropped (except ping) and no-new-privileges.

Explicit memory limits

This Pi kernel runs without the memory cgroup, so container limits do nothing and Java cannot size itself from them. The Hub sets its heap by hand (256 MB) and the stack stays around 1.5 GB of the 8 GB.

Nothing public listens

Public access is an outbound tunnel. The private dashboard is reachable only from the home network and the Tailscale VPN. SSH is key-only.

Backups

Pi to Proxmox Backup Server

  1. Every Sunday at 06:00 cron runs a small wrapper script.
  2. It uploads the root filesystem as one archive, skipping volatile folders.
  3. The server de-duplicates, so a normal run sends about 2 GB of 12 GB.
  4. A dated log is written; the newest four are kept.

Hub data, twice

  1. The Hub copies its own database every day at 03:30 UTC and keeps the newest 14.
  2. The weekly system backup also contains the whole Hub data folder.
  3. Before every risky change a manual copy of the database and dashboard file is taken.
Honest limit. The backup server lives on the Proxmox machine, which is powered on demand. A Sunday run only succeeds if that machine is awake, and a missed week is simply missing. Retention pruning and an off-site copy are on the roadmap.

If the USB stick dies, this is the order that gets everything back. Secrets always come from a password manager, never from the repository.

  1. Flash the OS. Raspberry Pi OS 64-bit (bookworm) to the USB stick with the imager: set the hostname, a user and your SSH public key. Keep the microSD in the slot as scratch.
  2. Pin the address. Create a DHCP reservation on the router, so the Pi is always at the same address.
  3. Install the base. Docker with the Compose plugin, ufw (default deny), wakeonlan, the Proxmox Backup client; join Tailscale and publish the dashboard with tailscale serve.
  4. Create the shared Docker network that Watchtower and the Hub's Docker page expect.
  5. Restore the Hub data from the backup server (or the newest daily database copy) before the Hub ever starts, so it never creates an empty database.
  6. Create the .env files from the checked-in example, which lists the variable names only.
  7. Start the stacks: tunnel connector, monitoring, Watchtower, then the Hub.
  8. Add the backup cron line and run it once by hand to prove the credentials.
  9. Create the restricted shell user the Hub's terminal and Docker pages log in as, and reuse it for every Hub feature.
Rule of the house: data first, containers second. An empty database that starts before a restore is the one way to turn a small outage into a data loss.
